# Backend и локальное хранение GYMIX

## Что работает сейчас

- Hono API, PostgreSQL и Drizzle; локальная PostgreSQL запускается отдельно от API.
- Регистрация и восстановление аккаунта требуют одноразового кода. Восстановление в grace-период не меняет пароль и deleted_at до проверки кода.
- Браузерная установка передаёт постоянный installationId (UUID) в login и verify-email. Без него каждый вход создаёт новое устройство. User-Agent — только подпись.
- Отзыв устройства отключает его сессии, но сохраняет строку для связей истории. Повторный вход с той же установкой возвращает то же устройство.
- Активную тренировку редактирует её устройство-владелец. Завершённую историю можно исправлять с любого авторизованного устройства пользователя.
- Журнал sync_operations и revision защищают повторную отправку и конкурентное редактирование. Каждый элемент пакета выполняется в savepoint; успешные элементы коммитятся вместе с журналом, отклонённые не оставляют побочных изменений.
- PGlite в браузере запускается в worker и разделяется между вкладками. Миграции выполняются до открытия доступа, журнал хранится в _gymix_migrations. Старый клиент без журнала принимается как baseline 0000 только при наличии всех таблиц. Данные не сбрасываются.
- PostgreSQL и новые браузерные базы получают одинаковые UUID справочников из packages/db/src/reference-ids.ts. При переименовании записи её UUID нужно сохранять в реестре. Существующие локальные UUID автоматически не переписываются.
- Production-сборка сайта содержит Service Worker, сохраняющий интерфейс, изображения и WASM для открытия без сети. Новый build активируется после закрытия вкладок предыдущей версии. Первый визит требует сети и завершения загрузки всего кэша. В dev-режиме Service Worker не регистрируется.

## Локальная PostgreSQL

```bash
pnpm db:up
cp apps/server/.env.example apps/server/.env  # только если .env ещё нет
pnpm db:prepare
pnpm server:dev
```

База приложения: `postgres://gymix:gymix@localhost:55432/gymix`.
Порт слушает только 127.0.0.1. Это локальные реквизиты разработки; production использует свои значения.
`pnpm db:stop` останавливает контейнер, сохраняя том. Смена `GYMIX_DB_PORT` в Compose требует изменения DATABASE_URL в apps/server/.env.

`pnpm db:prepare` применяет миграции и атомарно загружает справочники на пустую базу. Повторный запуск безопасен. При старте API выполняются те же действия, если APP_MIGRATE/APP_SEED включены.

## Контракт синхронизации тренировки

Общие схемы и типы операций: `@gymix/contracts`. Запрос `POST /api/v1/workouts/:id/ops`:

```json
{
  "expectedRevision": 1,
  "ops": [
    { "operationId": "UUID", "type": "set_add", "payload": { "sessionExerciseId": "UUID", "setNumber": 4 } }
  ]
}
```

В одном пакете 1–100 операций. Они видят результаты предыдущих элементов. ID операции нельзя повторно использовать с другим payload или другой тренировкой. Повтор уже применённого пакета принимается даже со старой expectedRevision; новые операции при несовпадении ревизии не применяются.

Для интеграций с этим endpoint подтверждения applied/skipped можно удалять из очереди; rejected нужно сохранять и показывать причину. Текущий браузерный клиент использует описанный ниже протокол снимков. При conflict нельзя слепо заменять expectedRevision и повторять старые значения: сначала нужно получить актуальное состояние и разрешить конфликт.

`GET /api/v1/workouts?limit=20&cursor=...` выдаёт завершённую историю и nextCursor. `GET /workouts/active` — отдельный список активных. `PATCH /workouts/:id` требует expectedRevision и проверяет согласованность дат.

## Проверки

```bash
pnpm check
pnpm build
```

По умолчанию серверные тесты используют PGlite. Для реального PostgreSQL создайте отдельную административную базу с суффиксом `_test`:

```bash
docker compose -f docker-compose.dev.yml exec -T db psql -U gymix -d postgres -c 'CREATE DATABASE gymix_test'
TEST_DATABASE_URL=postgres://gymix:gymix@localhost:55432/gymix_test pnpm --filter @gymix/server test
```

Тестовая роль должна иметь CREATEDB. Каждый тест получает отдельную временную базу со случайным именем, после проверки она удаляется. База приложения не очищается и не мигрируется тестами. CI проверяет PGlite, PostgreSQL 16 и обе сборки.

## Резервная копия PostgreSQL

Для локальной Compose-базы можно создать custom-format dump вне репозитория:

```bash
docker compose -f docker-compose.dev.yml exec -T db pg_dump -U gymix -d gymix -Fc --no-owner --no-acl > /private/tmp/gymix.dump
```

Восстанавливайте через `pg_restore --no-owner --no-acl --exit-on-error` в новую пустую базу. Рабочую базу не используйте для проверки восстановления. Для production нужны постоянное хранилище резервных копий, ограничение доступа и расписание; временный путь выше подходит только для локальной проверки. JSON-выгрузка браузера и дамп PostgreSQL решают разные задачи и не заменяют друг друга.

16 октября 2026 проверены `pg_dump` и восстановление в отдельную временную PostgreSQL-базу: число записей каталога, аккаунтов, тренировок и квитанций совпало. Временная база и dump после проверки удалены. Также проверен браузерный сценарий: старт онлайн → ввод и завершение без API/preview → закрытие и повторное открытие сайта → очередь на устройстве → возврат серверов → все три подхода `42,5 × 8` появились в PostgreSQL. Формы входа проверены при ширине 390 и 1440 px.

## Production

Основной docker-compose.yml требует POSTGRES_PASSWORD, JWT_SECRET, APP_ORIGINS и SMTP_HOST. Пароль БД в DATABASE_URL должен быть допустим для URI (спецсимволы нужно кодировать). SMTP_PORT/SMTP_SECURE/SMTP_USER/SMTP_PASS/MAIL_FROM задаются для конкретного провайдера. JWT_SECRET генерируется отдельно, минимум 32 символа. Dev-секрет и console-почта запрещены в production.

TRUST_PROXY включается только за прокси, который перезаписывает X-Forwarded-For и закрывает прямой доступ к API. Иначе лимитер использует адрес TCP-соединения. Счётчики пока в памяти одного экземпляра; для нескольких экземпляров потребуется общий лимитер.

## Аккаунт и офлайн-синхронизация клиента

Клиент поддерживает вход, регистрацию с подтверждением email и восстановление пароля. Для первого входа нужна сеть. Уже открытый аккаунт остаётся доступен без сети, даже если access-токен истёк. Ошибка обновления токена не очищает данные или очередь: интерфейс предлагает повторный вход.

PGlite хранится в отдельной IndexedDB-базе `gymix-account-<userId>`. Вкладки одного аккаунта используют общий worker. Токены хранятся в localStorage, обновление refresh-токена сериализуется Web Locks между вкладками. Выход удаляет локальную авторизацию, но сохраняет базу и неотправленные изменения. На общем компьютере это не заменяет защиту профиля браузера; очистка данных сайта удалит локальные копии.

Каждое локальное изменение и его запись в `local_outbox` коммитятся одной транзакцией. Это охватывает создание/завершение тренировки, подходы и паузы, исправления истории, шаблоны, исключения и вес тела. Новые сущности получают UUID в браузере. Неподготовленные изменения одной записи объединяются. После первой попытки отправки ID, payload и базовая версия фиксируются: потерянный ответ повторяется с тем же запросом, новые правки получают следующий элемент очереди.

Текущий клиент использует общие схемы `@gymix/contracts`:

- `POST /api/v1/sync/change`: `{ operationId, key, baseVersion, payload, claim }`. Ключи: `workout:<UUID>`, `template:<UUID>`, `weight:<YYYY-MM-DD>`, `exclusions:all`; `payload: null` означает удаление. Версия — SHA-256 канонического снимка записи.
- Сервер проверяет принадлежность аккаунту, версию и владение активной тренировкой. Изменение и квитанция `sync_receipts` атомарны. Повтор возвращает сохранённый ответ даже после удаления записи; повтор ID с другим запросом отклоняется.
- `GET /api/v1/sync/snapshot` возвращает согласованный полный снимок аккаунта. Отсутствие ранее известного ключа означает удаление. Неотправленные локальные записи не заменяются при загрузке.
- Передача активной тренировки другому устройству требует явного действия и сети. Старый владелец не может отправить правки поверх нового состояния. Конфликт сохраняет локальный вариант и предлагает выбор; перед разрешением оба варианта и очередь архивируются в `local_recovery`.

Синхронизация запускается при открытии, изменениях, возврате на вкладку, восстановлении сети и периодически. Web Locks исключают одновременную отправку из нескольких вкладок. Исправление истории проверяет ревизию, с которой открыта форма, чтобы не затереть обновление, пришедшее во время ввода.

В настройках и при ошибках доступна JSON-выгрузка локальных данных, исходящей очереди и архивов конфликтов без токенов и паролей. Автоматический импорт выгрузки пока не реализован. Старую техническую базу прежнего прототипа клиент не привязывает к реальному аккаунту автоматически.

Полный снимок выбран для текущего объёма проекта. Для большой истории следующий технический шаг — постраничный журнал изменений с курсором и tombstone. Тесты проверяют изоляцию аккаунтов, потерянный ответ, конфликт, удаление, передачу владения, завершение без сети и появление данных на втором устройстве.

Дизайн существующих экранов сохранён; добавлены необходимые формы входа и состояние синхронизации. `reference/` остаётся read-only.
