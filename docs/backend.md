# Backend и локальное хранение GYMIX

## Что работает сейчас

- Hono API, PostgreSQL и Drizzle; локальная PostgreSQL запускается отдельно от API.
- Регистрация и восстановление аккаунта требуют одноразового кода. Восстановление в grace-период не меняет пароль и deleted_at до проверки кода.
- Браузерная установка передаёт постоянный installationId (UUID) в login и verify-email. Без него каждый вход создаёт новое устройство. User-Agent — только подпись.
- Отзыв устройства отключает его сессии, но сохраняет строку для связей истории. Повторный вход с той же установкой возвращает то же устройство.
- Активную тренировку редактирует её устройство-владелец. Завершённую историю можно исправлять с любого авторизованного устройства пользователя.
- Журнал sync_operations и revision защищают повторную отправку и конкурентное редактирование. Каждый элемент пакета выполняется в savepoint; успешные элементы коммитятся вместе с журналом, отклонённые не оставляют побочных изменений.
- PGlite в браузере запускается в worker и разделяется между вкладками. Миграции выполняются до открытия доступа, журнал хранится в _gymix_migrations. Старый клиент без журнала принимается как baseline 0000 только при наличии всех таблиц. Данные не сбрасываются.
- PostgreSQL и новые браузерные базы получают одинаковые UUID справочников из packages/db/src/reference-ids.ts. При переименовании записи её UUID нужно сохранять в реестре. Существующие локальные UUID автоматически не переписываются.
- Production-сборка сайта содержит Service Worker, сохраняющий интерфейс, изображения и WASM для открытия без сети. Новый build активируется после закрытия вкладок предыдущей версии. Первый визит требует сети и завершения загрузки всего кэша. В dev-режиме Service Worker не регистрируется.

## Локальная PostgreSQL

```bash
pnpm db:up
cp apps/server/.env.example apps/server/.env  # только если .env ещё нет
pnpm db:prepare
pnpm server:dev
```

База приложения: `postgres://gymix:gymix@localhost:55432/gymix`.
Порт слушает только 127.0.0.1. Это локальные реквизиты разработки; production использует свои значения.
`pnpm db:stop` останавливает контейнер, сохраняя том. Смена `GYMIX_DB_PORT` в Compose требует изменения DATABASE_URL в apps/server/.env.

`pnpm db:prepare` применяет миграции и атомарно загружает справочники на пустую базу. Повторный запуск безопасен. При старте API выполняются те же действия, если APP_MIGRATE/APP_SEED включены.

## Контракт синхронизации тренировки

Общие схемы и типы операций: `@gymix/contracts`. Запрос `POST /api/v1/workouts/:id/ops`:

```json
{
  "expectedRevision": 1,
  "ops": [
    { "operationId": "UUID", "type": "set_add", "payload": { "sessionExerciseId": "UUID", "setNumber": 4 } }
  ]
}
```

В одном пакете 1–100 операций. Они видят результаты предыдущих элементов. ID операции нельзя повторно использовать с другим payload или другой тренировкой. Повтор уже применённого пакета принимается даже со старой expectedRevision; новые операции при несовпадении ревизии не применяются.

Клиент удаляет из будущей очереди только подтверждённые applied/skipped, сохраняет rejected и показывает причину. При conflict нельзя слепо заменять expectedRevision и повторять старые значения: сначала нужно получить актуальное состояние и разрешить конфликт.

`GET /api/v1/workouts?limit=20&cursor=...` выдаёт завершённую историю и nextCursor. `GET /workouts/active` — отдельный список активных. `PATCH /workouts/:id` требует expectedRevision и проверяет согласованность дат.

## Проверки

```bash
pnpm check
pnpm build
```

По умолчанию серверные тесты используют PGlite. Для реального PostgreSQL создайте отдельную административную базу с суффиксом `_test`:

```bash
docker compose -f docker-compose.dev.yml exec -T db psql -U gymix -d postgres -c 'CREATE DATABASE gymix_test'
TEST_DATABASE_URL=postgres://gymix:gymix@localhost:55432/gymix_test pnpm --filter @gymix/server test
```

Тестовая роль должна иметь CREATEDB. Каждый тест получает отдельную временную базу со случайным именем, после проверки она удаляется. База приложения не очищается и не мигрируется тестами. CI проверяет PGlite, PostgreSQL 16 и обе сборки.

## Production

Основной docker-compose.yml требует POSTGRES_PASSWORD, JWT_SECRET, APP_ORIGINS и SMTP_HOST. Пароль БД в DATABASE_URL должен быть допустим для URI (спецсимволы нужно кодировать). SMTP_PORT/SMTP_SECURE/SMTP_USER/SMTP_PASS/MAIL_FROM задаются для конкретного провайдера. JWT_SECRET генерируется отдельно, минимум 32 символа. Dev-секрет и console-почта запрещены в production.

TRUST_PROXY включается только за прокси, который перезаписывает X-Forwarded-For и закрывает прямой доступ к API. Иначе лимитер использует адрес TCP-соединения. Счётчики пока в памяти одного экземпляра; для нескольких экземпляров потребуется общий лимитер.

## Следующий этап: подключение аккаунта и синхронизация клиента

Это оставшаяся работа, а не уже реализованные функции:

1. Клиентская авторизация и отдельное локальное хранилище на аккаунт. Технический local@offline.gymix пока используется текущим UI; гостевой режим в продуктовой V1 по-прежнему не заявляется.
2. Транзакционная исходящая очередь вместе с локальным изменением; клиентские UUID для создания тренировок и их элементов, идемпотентный create на сервере.
3. Загрузка изменений с сервера, включая шаблоны, исключения, вес тела, историю и удаления. Версии/tombstone или отдельный журнал изменений; одних текущих ops активной тренировки недостаточно.
4. Сохранение отклонённых офлайн-изменений при передаче владения другому устройству, без молчаливой потери данных. Точный пользовательский сценарий предстоит реализовать.
5. Изолированное хранение авторизации, обработка истечения сессии без потери локальной очереди, резервное копирование и проверка восстановления серверной базы.

Дизайн существующих экранов не менялся. `reference/` остаётся read-only.
