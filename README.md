# GYMIX

Трекер тренировок для спортзала. Приложение для подбора упражнений по типу
тренировки и уровню объёма, ведения реальных подходов и графиков прогресса.

## Что в репозитории

Монорепозиторий: домен вынесен в переиспользуемые пакеты, `apps/client` и
`apps/server` — приложения, `reference/` — спецификация и данные.

```text
.
├── apps/
│   ├── client/          React + Vite + PGlite — офлайн-клиент с синхронизацией
│   └── server/          Hono + PostgreSQL — REST API
├── packages/
│   ├── structures/      Матрица «формат × объём», модель слота
│   ├── contracts/       Общие типы и валидация API
│   ├── catalog/         Каталог упражнений из reference/ в типы
│   ├── generator/       Заполнение слотов упражнениями
│   └── db/              Схема Drizzle, миграции, seed (PostgreSQL + PGlite)
├── reference/           Канон: спецификации, решения, каталог, данные
├── docs/                Backend, офлайн-синхронизация и эксплуатация
├── scripts/             verify_sync.py — проверка канона
└── .github/workflows/   CI
```

| Путь | Что это | README |
|---|---|---|

### Стек

TypeScript везде, один монорепозиторий на pnpm workspaces + Turborepo.
Сервер и клиент на одном языке, чтобы модель данных не расходилась в двух
местах. База — PGlite (PostgreSQL в WASM) на клиенте для оффлайна в зале и
PostgreSQL на сервере, одна схема на Drizzle и одни миграции для обоих.

## Команды

```bash
pnpm install
pnpm db:up      # локальная PostgreSQL, порт 55432
pnpm db:prepare # миграции и справочники
pnpm build      # production-сборки клиента и сервера
pnpm test        # тесты доменного слоя и сервера
pnpm typecheck   # строгий TypeScript, включая тесты
pnpm check       # типы + типы E2E + тесты + проверка канона, то же что в CI

pnpm exec playwright install chromium # один раз: браузер для E2E
pnpm e2e         # браузерные сценарии на локальной PGlite с заглушкой API
pnpm e2e:typecheck

pnpm server:dev  # бэкенд в режиме разработки
pnpm server:build
pnpm server:start

pnpm --filter @gymix/client dev   # клиент, http://localhost:5173
pnpm --filter @gymix/client build
```

Пакеты отдают друг другу исходники напрямую (JIT), отдельная сборка нужна
только серверу (`tsup`, один ESM-бандл) и клиенту (`vite`).

Папки-дубли нет намеренно: раньше `sources/` была копией `reference/`, и держать
два одинаковых набора файлов смысла не имело.

Текущий backend, запуск PostgreSQL и границы готовности синхронизации: [docs/backend.md](docs/backend.md).

### Браузерные тесты

`e2e/` — Playwright-сценарии на реальном клиенте: полный цикл тренировки и
шаблона, история и редактирование записи, офлайн-черновик, axe (WCAG AA),
переполнение на 320/393/820 px, 200% текста и reduced motion. Тесты поднимают
dev-сервер сами (`playwright.config.ts`), работают на локальной PGlite и
подменяют `/api/v1/**` ответом 503 — сервер и база для них не нужны. Артефакты
упавших прогонов (`playwright-report/`, `test-results/`) сохраняет CI.

Ключевые решения, структура каталога и что уже закрыто — в
[`reference/README.md`](reference/README.md).

## Соглашения разработки

- **Пакеты `packages/*` — домен и данные**, без побочных эффектов на импорте;
  приложения `apps/*` собираются из них. Направление зависимостей только
  «вниз»: `apps → packages`, `generator → catalog → structures`, без циклов.
- **Один пакет — один `tsconfig.json`** (в `packages/*` — `noEmit` для
  проверки, сборка не нужна). Общая база — `tsconfig.base.json`.
- **Тесты рядом с кодом**, в `test/` внутри пакета, `vitest run`. Один `test`
  на пакет; турбо гоняет их параллельно.
- **Каждый пакет объявляет свои зависимости сам** (включая `typescript`,
  `vitest`, `@types/node`) — манифест самодостаточен.
- **`exports` отдаёт `./src/*.ts`.** Публичная поверхность пакета — только то,
  что перечислено в `exports` и в его `src/index.ts`.
- **Стиль:** 2 пробела, LF, финальный перевод строки — см. `.editorconfig`.
  Версия Node зафиксирована в `.nvmrc` (22) и в `engines`.

## Канон

Канон — **оба DOCX**. Markdown-файлы в `reference/` считаются заметками: они
повторяют ключевые числа и решения спецификации, но не обязаны быть её полным
отражением. В DOCX есть разделы, которых нет в Markdown (описание статусов,
разделы 7–19), поэтому генерировать DOCX из Markdown нельзя: потерялось бы
около трёх четвертей содержания.

## Проверка согласованности

```bash
python3 scripts/verify_sync.py
```

Скрипт ничего не исправляет — он падает с кодом `1` и печатает список
расхождений. Проверяет:

- целостность обоих DOCX: ZIP и все XML-компоненты;
- что ключевые утверждения (матрица объёмов, вход, срок жизни сессии, правила
  графика) звучат одинаково в DOCX и заметках рядом;
- что запрещённые формулировки не вернулись: диапазоны объёмов, имя «Ягодицы»,
  сырая markdown-разметка;
- арифметику каталога: 118 размещений, 113 уникальных, 5 межгрупповых дублей,
  11 записей «Пресса», сходятся счётчики групп в заголовках;
- что группа «Пресс» во всех файлах помечена как недостижимая для генератора.

Перед коммитом прогонять обязательно. Если упало — сначала пойми, что именно
разошлось: по правилам проекта канон меняется в DOCX, заметка правится рядом.
То же делает CI: `.github/workflows/check.yml` запускает `pnpm check` на каждом
пуше в `main`.

## Каталог как данные

Перечень упражнений каноничен в `reference/exercise_catalog_v1.md`, и код его
не дублирует: `loadCatalog()` читает документ при запуске. Правка классификации
делается в файле, а тесты падают, если документ разошёлся с каноном — например
если число в заголовке раздела перестало совпадать с числом строк или у записи
исчез паттерн.
